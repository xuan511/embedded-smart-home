# 毕设实施、演示与实验记录

题目：《智能家居环境监测与控制系统的设计与实现》。本工程适合作为“能够说明原理、接线与异常处理”的双板环境监测和控制毕设。当前优先事项是取得可重复的真机记录。完整操作从[零基础教程](BEGINNER_GUIDE.zh-CN.md)开始，官方依据统一见[手册对应表](OFFICIAL_REFERENCE.md)。

## 1. 毕设应该完成什么

把演示目标限定为：真实传感器采集 → STM32 执行/上报 → USB 转串口 → Korvo 显示 → 触摸/串口/手机请求 → STM32 执行 → 回报；Korvo 同时向局域网 MQTT Broker 上传状态。

| 需求编号 | 必须具备的行为 | 主要实现 | 如何验收 |
| --- | --- | --- | --- |
| R01 | 温度、湿度、光照约 1 秒更新 | STM32 sensors/board、home_core、USB/显示 | 阶段 3/4 真实 source；留存读数及变化记录 |
| R02 | 灯/两线低压风扇开关 | STM32 PB0/PB1 → 驱动级 | 分别记录回报与实际动作，不用 GPIO 直接供电 |
| R03 | 手动/自动与滞回 | STM32 controller + home_core | 上/下阈值及中间区分别测试，避免只测一次开关 |
| R04 | 阈值保存、上电/重连同步 | Korvo NVS、home_remote CONFIG | 保存、分别复位两板、检查期望值与 synced |
| R05 | 故障、失联和过期可见 | STM32 有效位、Korvo 年龄与会话 | 单传感器故障、拔 USB、暂停 STM32 的不同结果 |
| R06 | LCD/触摸控制和必要状态 | BSP + ui.c | 读数、来源、模式、输出、USB/参数/MQTT/SD 与操作结果 |
| R07 | 每秒 MQTT 遥测 | Korvo ESP-MQTT、PC Broker | 实际订阅 JSON、停止/恢复 Broker、检查旧数据不回放 |
| R08 | 同网段微信小程序 | 带令牌 HTTP API、小程序 | 自己的 AppID 手机预览，带 ID 的请求和 ACK，手机离线 |
| R09 | 可复现工程 | 固定依赖、STM32 启动/链接、教程/CI | 新目录按文档重新构建，记录工具版本与提交 |

这些需求与 1 秒采样、3 秒链路判定、约 5 秒手动保护、滞回、HTTP 字段等属于**本项目设计**。厂商资料支持的是接口、电气条件、指令和驱动 API，不意味着官方规定或认证了这些毕设指标。

不扩展 PWM/转速采集、AI/语音、云平台、独立手机 App、Matter、OTA、相机或自研 PCB。现有板载自检为附录，不计入环境监测主线验收。

## 2. 哪些设计应该能解释清楚

| 问题 | 本项目的具体回答 | 证据位置 |
| --- | --- | --- |
| 为什么用两块板？ | 保留 Korvo 原配显示、触摸和 SD；把可接线传感器/执行器放到 STM32 | HARDWARE、BSP、Korvo 官方原理图 |
| 两板“USB 连接”是什么？ | Korvo USB-A Host → 指定 CP2102/CP2102N → STM32 PA9/PA10 UART；不是学习板 USB 插座 | USB Host/CP210x 官方 API 和实际连接表 |
| 谁控制真实负载？ | STM32 是输出状态与自动规则的唯一执行者；Korvo 是操作、显示、参数中枢 | ARCHITECTURE、home_remote、stm32_controller |
| 为什么不用 STM32 原生 USB？ | 板型/插座线路和 USB 时钟条件未确认；所选桥路径有明确接口和官方驱动 | HARDWARE；这是项目取舍 |
| 为什么有两个阈值？ | 温度/照度在边界附近波动时，中间区保持输出，减少反复开关 | home_core 与边界测试；这是自定算法 |
| 为什么保存放 Korvo？ | NVS 有持久化实现；STM32 只保留当前会话运行副本，避免两边旧参数互相覆盖 | NVS 文档与同步顺序 |
| 手机必须走 MQTT 吗？ | 本版 Korvo 用 MQTT 上传；手机用同网段 HTTP 向 Korvo 请求控制，省去额外后端与 WS 服务 | NETWORK、微信官方局域网规则 |
| ACK 能证明风扇转了吗？ | 只能证明收到 STM32 的操作结果/输出回报；实际旋转、灯亮灭需另行观察 | API 的 physical_feedback=false、验收视频 |

## 3. 先按这一顺序做实验

1. **通信阶段**：先不接传感器/负载，烧阶段 1；记录枚举、HELLO/READY、同步、拔插。没有真实读数是预期。
2. **测试数据阶段**：阶段 2 的 30℃/55%/50 lx 必须标明 TEST，记录 LED 控制与 ACK。默认 AUTO 的灯阈值可能让 LED 一开始就亮；先理解模式再判断。
3. **传感器阶段**：阶段 3 接 SHT3x-DIS/BH1750，观察环境趋势和单通道故障。记录准确模块型号、地址、供电与上拉。
4. **负载阶段**：阶段 4 按教程接 MOSFET/独立低压电源。启动默认 AUTO，同步后即可自动动作；先确认手动并关闭两路，再按教程接通负载电源。记录实际电压、电流额定值和驱动型号。
5. **参数/异常阶段**：分别验证保存、未保存、两板复位、USB 失联、数据过期、传感器故障；不要只测网络断开。
6. **网络阶段**：先 Korvo 取得 IP，再 PC 订阅 MQTT，最后手机预览；每加入一层重新确认前面的真实闭环仍可运行。
7. **连续运行**：先 30 分钟，再按课题要求做 2 小时或更长；没有实际记录的时长填写“未进行”。

实际操作与接线以 [BEGINNER_GUIDE](BEGINNER_GUIDE.zh-CN.md)、[HARDWARE](HARDWARE.md)、[ACCEPTANCE](ACCEPTANCE.md)、[NETWORK](NETWORK.md) 为准，下面是记录方法，不替代它们。

## 4. 拟定验收门槛与测量方法

以下是建议给导师确认的**项目验收目标**，没有实测前不填“已达到”，也不是引用的厂家保证值。

| 项目 | 拟定门槛/判据 | 测量方法与限制 |
| --- | --- | --- |
| 采样/显示更新 | 名义约 1 Hz；记录实测间隔而不写绝对实时 | 用连续日志时间戳统计；HTTP 抓取周期不等于 STM32 采样精度 |
| 手动请求 | 排队、ACK、实际动作分别可见；无 ACK 显示未知 | 测请求到 ACK 的时间，再单独记录动作观察；HTTP 返回速度不是动作时间 |
| 温度自动控制 | ≥fan_on 开，≤fan_off 关，中间区保持 | 记录每次阈值、有效读数、前后输出，且先进入 AUTO |
| 灯自动控制 | ≤light_on 开，≥light_off 关，中间区保持 | 遮挡/恢复 BH1750，分别记录边界；无校准照度计时只证明趋势与联动 |
| 传感器故障 | AUTO 关闭对应输出并报告故障，另一有效规则继续 | 先断电调整接线，再恢复；MANUAL 不因传感器故障自动取消已有命令 |
| Korvo↔STM32 失联 | Korvo 约 3 秒内过期/断线；STM32 MANUAL 约 5 秒关闭演示负载 | 从拔 USB 到显示/实际关断各计时；主循环传感器事务可能带来调度误差，记录实测最大值 |
| Wi-Fi/MQTT/手机失联 | 本地显示和 STM32 有效自动规则继续；网络状态正确变化 | 这几种断线不会停止 USB 心跳，也不等同于手动 5 秒关断 |
| 参数 | 保存值两板重启后恢复并同步；未保存值按文档区别 | 不用先前 RAM 数字冒充掉电保存 |
| 连续运行 | 建议先 30 分钟无非预期复位/挂死；所有异常均有记录 | 复位、USB、传感器、网络异常分别计数，解释已主动注入的故障 |
| 资源占用 | 链接不超过 STM32 64KB/20KB，保留清晰资源表 | .map/.elf 与编译日志；链接预留栈不是最大实测栈使用量 |

传感器精度应以**实际订货型号、工作条件与厂家手册**为准。没有参考仪器和重复测量时，不写“温度误差 ±0.1℃”“精度满足厂家指标”或“照度已校准”。不能把软件显示的小数位数当测量精度。

如果现场不方便改变温度，可修改阈值触发联动并清楚说明“改变阈值演示规则”；这不能被记录为一次真实升温实验。温度/光照随环境变化的真实记录另做。

## 5. 连续运行记录工具

在设备已通过阶段 4、联网且正常采集后，从仓库根目录运行，换成实际 IP：

```powershell
python tools/live_check.py --ip 192.168.1.50 --seconds 1800 --output records/run-01.jsonl
```

需要同时考察 MQTT 回报的运行检查：

```powershell
python tools/live_check.py --ip 192.168.1.50 --seconds 1800 --require-mqtt --output records/run-02.jsonl
```

令牌交互输入，不写日志。脚本只读，不会开关负载。输出是每行一个 JSON 的 JSONL 文件，第一行为 start，中间为状态与 HTTP 耗时，最后为 end 汇总。已有日志不覆盖；Ctrl+C 会标注 interrupted，不能把中断的检查记为完整时长通过。

检查会拒绝 TEST/模拟、错误阶段、空/布尔/非有限/超范围读数、故障、失联、参数未同步及过期年龄；只说 stale=false 而年龄已过门槛也不能通过。出现 Korvo uptime 下降会计入 observed_korvo_resets，相同 uptime 会报停滞。它**不能计数未观测到的复位，也不测 STM32 复位次数**；STM32 的复位/上电需现场记录。

`failures` 是异常 HTTP 抓取次数，不是串口坏帧数、传感器坏样本数或故障事件次数。`http_response_ms` 是 HTTP 往返耗时，不是风扇动作延迟。检测到复位即使后来恢复也保留失败记录；不要删掉异常样本来生成“稳定运行”的结论。

## 7. 5～8 分钟答辩演示建议

| 顺序 | 展示内容 | 需要解释 |
| --- | --- | --- |
| 1 | 展示两板和清晰的接线表 | 为什么保留 Korvo 屏/SD，外设接 STM32，USB 桥是什么 |
| 2 | source=sensor 的实时读数 | 与 TEST 和 SIMULATION 区别；约 1 秒周期和有效性 |
| 3 | 触摸/手机手动开关灯与风扇 | 请求、STM32 回报、实际动作三类证据 |
| 4 | 切 AUTO，遮光/恢复或演示阈值规则 | 哪块板执行规则、上下阈值和中间区 |
| 5 | 展示 MQTT 订阅与阈值保存 | 上传到哪台 PC；NVS 权威与重连同步 |
| 6 | 只演示一种已经排练通过的异常 | USB 断开与网络断开不同；不要临场扩线或更换驱动 |
| 7 | 打开实测表、完整日志和编译资源表 | 哪些编译/主机验证通过，哪些有真机依据，哪些仍未验证 |

论文可以围绕需求与取舍、总体设计、接口与供电、驱动与协议、状态归属、界面、测试方法与实测结果展开。厂商的器件事实引用原始手册；本项目的协议/算法引用自己的设计与代码；测试结论指向自己留下的准确版本和原始数据。不要把官方接口支持、CI 通过或主机夹具写成整机真机认证。
